1What are we building?

The problem. Ask a general-purpose LLM “revenue per customer?” and it happily writes SQL against tables it has never seen: it guesses names like clients.total_revenue. It knows SQL, but not your database.

Our fix. At question time, retrieve the relevant part of the user's schema and give it to the model (that's RAG), then let a small team of agents validate, fix, secure and explain the SQL.

HTTP in one picture

The browser and our API talk in requests and responses. Every request has a method + path, headers (metadata) and an optional body (data, here JSON).

Status codes we actually use

401 vs 403?
401: “I don't know who you are” (authentication failed). 403: “I know who you are, and you may not do this” (authorization failed).
The old API returned 200 with {"error": …} on failures, so the frontend couldn't use response.ok. Now every error has a real status + one JSON envelope: {"error": {code, message, details}}.

The server stack

  • Uvicorn: the actual network server. Opens the port, parses raw HTTP bytes.
  • ASGI (Asynchronous Server Gateway Interface): the standard “plug shape” between async servers and Python apps. Successor of WSGI (sync).
  • FastAPI = Starlette (routing, middleware, requests) + Pydantic (validation) + type hints → automatic OpenAPI docs at /docs.
  • Middleware wraps every request (CORS headers, later: request IDs, rate limits).
  • Router groups endpoints: we mount everything under /api/v1 so v2 can live next to it.
Versioned URLs (/api/v1) let you change the API without breaking old clients.

Pydantic: the bouncer at the door

class SignupRequest(BaseModel): name: str = Field(min_length=1, max_length=100) email: NormalizedEmail # EmailStr + lower() password: Password # 8+ chars, ≤72 bytes

Why it matters: the handler can trust its inputs. Validation, type conversion and error messages come for free from type hints.

Response models work the other way round: response_model=UserRead only lets declared fields out, so hashed_password can never leak in a response.

2 · Web backend foundationsBUILT ✓ phase 0

async / await & the event loop

Analogy: one waiter (the event loop thread), many tables (requests). A sync waiter stands at the kitchen until each dish is ready. An async waiter places the order (await), serves other tables, and comes back when the kitchen rings.
  • async def + await means “I'm waiting on I/O (network, disk, DB): run something else meanwhile”.
  • It only helps I/O-bound work. CPU-heavy work (embedding 10k chunks) still blocks → run it in a worker / process pool.
  • Inside async def, use async libraries only: asyncpg, httpx, LangChain's ainvoke.
Old code called the sync Groq client inside async def. One slow LLM call froze the whole server for every user.
result = await chain.ainvoke(inputs) # need a blocking lib? offload it: data = await asyncio.to_thread(fn)
Is async the same as multithreading?
No. Async is one thread switching between tasks at await points (cooperative). Threads are scheduled by the OS (preemptive). Async scales to thousands of waiting connections cheaply; it doesn't make CPU work faster.

3The data layer

Why PostgreSQL (and not Mongo) for us

  • Our data is relational: users → history; soon workspaces → schemas → tables → columns → foreign keys.
  • Constraints in the DB (UNIQUE email, FOREIGN KEY, NOT NULL) hold even when app code has a bug.
  • ACID transactions: all-or-nothing writes.
  • Still flexible: JSONB columns, full-text search, extensions.
UUID primary keys instead of 1, 2, 3…
  • not guessable (/history/5 → “let me try 6”)
  • can be generated anywhere (workers) before insert
  • cost: 16 bytes, random B-tree inserts (UUIDv7 fixes ordering)

Our schema today (ER diagram)

Read the crow's foot: one user (1) has many history rows (N). Deleting a user deletes their history automatically (ON DELETE CASCADE), done by Postgres, not by our code.
MongoDB was removed entirely. Its old history route never awaited the async driver, so nothing was ever saved.

Connecting to PostgreSQL

pgAdmin and our API are both just clients of the same PostgreSQL server. They log in with the same kind of credentials; ours live in backend/.env, and every part of the backend reads them from one place.

Anatomy of a connection URL

ThingWhat it is
PostgreSQL serverthe program listening on port 5432 (a Windows service); it holds many databases

-- pgAdmin → Query Tool, ONE statement at a time CREATE ROLE sqlassist WITH LOGIN PASSWORD '…'; CREATE DATABASE sql_assistant OWNER sqlassist;

Run them one by one (CREATE DATABASE can't run inside a transaction block), then alembic upgrade head. Edited .env? A running server keeps the old values until it restarts: our dev command restarts on .env changes.

Two passwords, don't mix them up. pgAdmin's master password only encrypts the logins pgAdmin saves; it never goes in .env. And a password like p@ss#1 breaks a hand-written URL (the @ looks like the host separator), which is why we build it with URL.create().
Why not let the app log in as postgres?
Least privilege: if the app is compromised (SQL injection, leaked .env), a superuser could drop every database or even run OS commands (COPY … PROGRAM). A role that only owns sql_assistant limits the damage to that database.

ORM: objects ⇄ rows

class User(UUIDPrimaryKeyMixin, TimestampMixin, Base): __tablename__ = "users" email: Mapped[str] = mapped_column( String(320), unique=True, index=True) queries: Mapped[list["QueryHistory"]] = relationship( back_populates="user", passive_deletes=True)

Session = unit of work. db.add(user) stages it, await db.commit() sends the INSERT and commits the transaction. On error: rollback(), nothing half-written.

Mixins share columns (id, created_at) across models without copy-paste.

Connection pool

Opening a Postgres connection costs a TCP + auth handshake. The engine keeps a pool of open connections; each request borrows one and returns it. pool_pre_ping=True tests a connection before use (the server may have dropped it).

expire_on_commit. After commit, SQLAlchemy normally “forgets” loaded values and reloads them lazily. In async code a lazy load can't happen implicitly → MissingGreenlet error. We set expire_on_commit=False.
What is the N+1 query problem?
Loading 1 list query, then 1 extra query per row for a relationship (N rows → N+1 queries). Fix with eager loading (selectinload) or a JOIN.

Migrations: git for your schema

uv run alembic revision --autogenerate -m "msg" uv run alembic upgrade head # apply all uv run alembic downgrade -1 # undo last uv run alembic check # drift?
Autogenerate is a draft. Ours was generated against SQLite, so it wrote (CURRENT_TIMESTAMP) + SQLite batch ops. We rewrote it by hand to portable SQL. Always read a migration before running it.

Indexes: the phone book trick

  • A B-tree index keeps keys sorted in a shallow tree → lookups in O(log n) instead of scanning every row.
  • Composite index (user_id, created_at) answers WHERE user_id = ? ORDER BY created_at DESC in one walk. Leftmost-prefix rule: it helps queries on user_id alone, but not on created_at alone.
  • Unique index on email: the DB rejects duplicates even if two signups race; we catch IntegrityError → 409.
  • Cost: faster reads, slower writes + disk. Index what you filter, join and sort on.

4 · Security basicsBUILT ✓ phase 0

4Security basics

Hashing ≠ encryption

  • We never need the original password, only to check it → store a hash. A leaked DB ≠ leaked passwords. (The old code stored plain text.)
  • Salt: random bytes mixed in per password. Same password → different hashes → precomputed “rainbow tables” are useless. Our test asserts hash("x") != hash("x").
  • bcrypt is slow on purpose: cost 12 = 212 rounds (~0.25 s). Fine for one login, brutal for billions of guesses. Fast hashes like SHA-256 are wrong for passwords.
72-byte limit. bcrypt ignores bytes after 72 (and bcrypt 5 raises an error). We reject longer passwords, counting bytes, not characters: one emoji = 4 bytes.
User enumeration. If “unknown email” answers faster than “wrong password”, attackers learn who has an account. We return the same message and still run bcrypt against a dummy hash.

4 · Security basicsBUILT ✓ phase 0

Anatomy of a JWT

  • Signed, not secret: anyone can decode the payload (try jwt.io). Never put secrets in it.
  • The server recomputes the signature with its SECRET. Change one character of the payload → signature mismatch → rejected.
  • Stateless: verifying needs no DB lookup (we still load the user to check is_active).
  • Claims: sub who · exp expiry · iat issued-at · jti unique id (enables revocation lists) · type our own: access or refresh.
Weak secret. HS256 needs ≥ 256 bits of randomness. Ours was 13 characters → rotated to secrets.token_urlsafe(48), and config now refuses < 32 chars at startup.
Pin the algorithm. jwt.decode(…, algorithms=["HS256"]) blocks the classic "alg": "none" and algorithm-confusion attacks.
# core/security.py (PyJWT) payload = jwt.decode(token, SECRET, algorithms=["HS256"], options={"require": ["exp", "sub", "type"]}) if payload["type"] != expected_type: raise jwt.InvalidTokenError()
Why did we add a “type” claim?
Without it, a long-lived refresh token would also work as an access token on every endpoint, defeating short expiry. A test checks this can't happen.

4 · Security basicsBUILT ✓ phase 0

Access + refresh tokens, step by step

Why two tokens? The access token travels on every request, so it's short-lived: if stolen, damage lasts minutes. The refresh token is sent to one endpoint only, rarely.

Single-flight refresh (frontend/src/lib/api.js): when 4 requests hit 401 at once, they all await one shared refresh call. We saw exactly this in the browser network log during testing.

// api.js: share one refresh between callers let refreshInFlight = null function refreshTokens() { refreshInFlight ??= fetch("/auth/refresh", …) .then(saveTokens) .finally(() => (refreshInFlight = null)) return refreshInFlight }
JWTs are stateless. How do you log someone out before the token expires?
You can't “un-sign” a token, so you add a little state back:
  • short access tokens (ours: 15 min) bound the damage window;
  • denylist the token's jti in Redis until its exp, checked in get_current_user;
  • refresh-token rotation: each refresh issues a new refresh token and invalidates the old one; if an old one is ever reused, it was stolen, so revoke the whole family;
  • token version on the user row: bump it on password change → every older token fails.
This is exactly why our tokens already carry a jti (unique id): revocation can be added in phase 8 without changing the token format.

4 · Security basicsBUILT ✓ phase 0

IDOR: the bug we had

Insecure Direct Object Reference: the API trusts an id from the URL without checking ownership. The old GET /user-data/{user_id} returned any user's data to anyone, no token needed.

  • Identity comes from the verified token, never from the URL or body.
  • Every query is scoped: WHERE user_id = :current_user. Test: Bob cannot list or delete Alice's history.
  • For someone else's row we return 404, not 403: don't even confirm it exists.

CORS (Cross-Origin Resource Sharing)

Different port = different origin. Browsers block JS from reading cross-origin responses unless the server allows that origin (CORS_ORIGINS setting). Requests with JSON or an Authorization header first send an OPTIONS preflight. CORS protects users' browsers; it is not API authentication (curl ignores it).

5LLM fundamentals

An LLM predicts the next token

  • Token = a chunk of text (≈ 4 characters of English). Models read, bill and limit in tokens.
  • Autoregressive: generate one token, append, run again. That's why long answers are slower.
  • Context window = max tokens seen at once (input + output). gpt-oss: ~131k. System prompt, schema, history and answer all compete for it.

Temperature reshapes the probability distribution before sampling: low = almost always the top token (we use 0.1 for SQL), high = more random/creative.

Hallucination = fluent but false output (an invented column). You don't “fix” it inside the model; you reduce it with grounding (RAG), validation (sqlglot) and checking agents.
Same prompt, different answers. Why?
Sampling: with temperature/top-p > 0 the next token is drawn at random from the distribution. Even at 0, batching and GPU math can add tiny non-determinism.

LangChain: chains of Runnables

  • LCEL (LangChain Expression Language): the | operator composes Runnables into a RunnableSequence; output of one = input of the next.
  • Why LangChain? Swap providers (ChatGroq ⇄ ChatOpenAI) without rewriting code, standard message/tool types, and LangGraph (phase 6) is built on it.
  • Defensive parsing: models sometimes ignore “no markdown” and wrap SQL in ```sql fences. extract_sql() unwraps them. Phase 1 adds structured output on top (next pages).
# services/sql.py chain = prompt | llm | StrOutputParser() try: text = await chain.ainvoke(inputs) except Exception as exc: raise LLMServiceError() from exc # → 502

Resilience: max_retries=2 retries rate limits (429) and server errors with exponential backoff; timeout=60s stops hung calls.

Testing LLM code: FakeListChatModel returns scripted replies: fast, free, deterministic. Test the plumbing with fakes; measure the model with evals (chapter 7).

Why not just call the Groq SDK directly?
For one call, you could. But we'll need prompt templates, structured outputs, tool calling, streaming, tracing and agent graphs across several providers. LangChain standardises those interfaces, so swapping a model or adding a retriever is one line instead of a rewrite.

Free text is for people; code needs fields it can trust. We describe the answer as a Pydantic class, LangChain turns it into a JSON Schema, and Groq's decoder is only allowed to produce JSON that matches it.

A prompt is a request; the model can still add a sentence or forget a field. Constrained decoding makes invalid output impossible, so parsing never fails on format.

5 · LLM fundamentalsBUILT ✓ phase 1

Reasoning models think before they answer

gpt-oss first writes hidden reasoning tokens (a scratchpad), then the visible answer. You never see them, but you wait for them and pay for them. Measured on our explain endpoint:

  • Reasoning tokens are output tokens: billed at the output price and counted toward max_tokens (ours: 4096).
  • reasoning_effort (low / medium / high) is our per-request “Thinking” switch. Defaults per prompt: generate = medium (correctness), explain = low (just describing).
  • Raw reasoning is kept away from users: providers advise against showing a model's unfiltered chain of thought. We store only the count.
Cost of one real “generate” call (gpt-oss-120b list prices):
356 input × $0.15 / 1M = $0.0000534 202 output × $0.60 / 1M = $0.0001212 total ≈ $0.000175
≈ $0.17 per 1,000 queries · free tier: $0, but rate-limited.
Money is not a float. In binary floating point 0.1 + 0.2 = 0.30000000000000004. Costs use Python Decimal and PostgreSQL NUMERIC(12, 8): exact decimal arithmetic.
What is time to first token (TTFT), and how did we cut it?
The wait until the first visible word: network + queue + prompt processing + hidden reasoning. Low effort removed ~1,100 reasoning tokens from explanations, so the first word arrives in 0.69 s instead of 1.72 s.

5 · LLM fundamentalsBUILT ✓ phase 1

Streaming: show words as they're written

SSE = one ordinary HTTP response that stays open, with the server writing events into it. One-way, plain HTTP, works through proxies: exactly what token streaming needs. (WebSockets are for two-way traffic, like chat or games.)

HTTP/1.1 200 OK Content-Type: text/event-stream event: token data: {"text": "Lists each"} event: token data: {"text": " department"} : ping ← keep-alive comment event: done data: {"output": "…", "usage": {…}}
  • FastAPI: the route is an async def that yields ServerSentEvents, with response_class=EventSourceResponse. Keep-alive pings every 15 s come free.
  • Browser: EventSource can only do GET without headers. We need POST + a Bearer token, so we read fetch()'s body stream and split events at blank lines (network chunks don't line up with events).
  • Cancel: an AbortController stops the fetch; the server notices the disconnect and stops generating.
The 200 status is sent with the first byte. Auth and validation run before the stream starts (normal 401/422 JSON); anything that fails later can only be an event: error.
Our rule: structure what code consumes (generate, debug, optimize: validated SQLAnswer), stream what people read (explain: markdown prose).
Why stream at all if the total time is the same?
Perceived latency. Reading can start after ~0.7 s instead of after the full answer, and a long answer shows visible progress instead of a frozen spinner.

When the LLM fails: retry or fall back?

  • Retry the same thing when the failure is probably temporary: dropped connection, timeout, provider 5xx.
  • Fall back to something else when waiting won't help soon: rate limit (429), one model's outage.
  • Exponential backoff: wait 0.5 s, 1 s, 2 s… so a struggling server gets room to recover.
  • Jitter (randomness) spreads clients out so they don't retry in synchronized waves: the thundering herd.
The hidden retry we found. By default the Groq SDK retries a 429 by itself, sleeping for the server's Retry-After (up to 60 s) each time. With 2 retries, one request could hang ~2 minutes before our code ran. Fix: ChatGroq(max_retries=0) + LangChain with_retry(TRANSIENT_ERRORS) + with_fallbacks(exceptions_to_handle=(RateLimitError,)). Lesson: know your SDK's defaults.

Tracing: see inside every LLM call

A trace is the tree of steps one request went through, each with timing, inputs and outputs (a span or run). For LLM apps it answers “what exactly did we send, what came back, and where did the time go?”

What we record for every callhistory row (PostgreSQL)LangSmith trace
prompt version, model, reasoning effort✓✓ (tags + metadata)

full prompt messages, JSON schema, raw reply—✓

Turn it on: free account at smith.langchain.com → API key → in backend/.env set LANGSMITH_TRACING=true and LANGSMITH_API_KEY. LangChain then traces every chain automatically, and LangGraph later traces agents too.

The LangSmith SDK caches environment variables on first read, and pydantic-settings doesn't export .env to the environment. So configure_tracing() copies them once at startup, before any LLM call.
Privacy: traces contain prompts and answers, so user questions and SQL leave your server. Fine for development; production needs consent, redaction, or a self-hosted tracer (Langfuse).
Why tracing, not just logs?
Logs are flat lines; a trace keeps the causal tree (which retry, which fallback, which prompt version) with timing per step: what you need to debug multi-step chains and, later, agents.

sqlglot turns SQL text into an AST (abstract syntax tree): typed nodes instead of characters. If the text can't be parsed for the chosen dialect, it isn't valid SQL, and sqlglot says where it broke.

CheckWhoPhase

6 · RAGCOMING · phases 2–4

Ingestion vs query pipeline

  • Ingestion is slow (OCR, embeddings) → it runs as a background job; the UI polls/streams progress.
  • Query is latency-critical → cheap steps use the fast model; the big model writes the SQL once.
  • Every stage is swappable and measurable separately; that's what makes evaluation (chapter 7) possible.
sqlglot is our secret weapon: it parses SQL in 20+ dialects into an AST (syntax tree). Ingestion uses it to extract tables/columns/keys; validation uses it to check generated SQL.

6 · RAGCOMING · phase 2

Chunking

A chunk is one retrievable unit of knowledge. Too big → noisy context and a blurry embedding. Too small → meaning gets cut in half.

StrategyIdeaGood for
fixed-size + overlapevery N tokens, overlapping a bitplain prose, quick baseline
recursivesplit by sections → paragraphs → sentencesdocuments with structure
semanticsplit where the meaning shifts (embedding distance)long mixed-topic text
structure-aware ✓split along the data's own unitsschemas (us), code, tables

Our unit: one table = one “card”

TABLE orders (schema: sales) Columns: id INT PK customer_id INT FK → customers.id total_amount DECIMAL(10,2) status VARCHAR(20) -- placed|shipped|refunded created_at TIMESTAMP About: one row per customer order. Synonyms: purchases, sales, transactions Joins: customers (customer_id), order_items (order_id)

Never split a CREATE TABLE in half: a chunk holding half the columns causes exactly the hallucinations we want to stop.

The About and Synonyms lines are written by the LLM during ingestion, so “purchases” finds orders.

Very wide tables (100+ columns) get extra column-group chunks that point back to their parent table.

Payload (metadata) travels with every chunk

{ "workspace_id": "w_42", "schema_id": "s_7", "table": "orders", "columns": ["id", "customer_id", "total_amount", "status", "created_at"], "fk_targets": ["customers", "order_items"], "dialect": "postgres" }
  • filter: search only the user's workspace, or only the tables they picked in the UI
  • explain: show the user which tables the answer was built from

6 · RAGCOMING · phase 3

Embeddings: meaning as coordinates

  • Cosine similarity compares directions: 1 = same meaning, 0 = unrelated, −1 = opposite. Length doesn't matter.
  • Bi-encoder: query and documents are embedded separately → document vectors are computed once at ingestion; search is just math.
  • Models come from the Hugging Face Hub (sentence-transformers) and run locally, free.
Use the same model for documents and queries. Changing the model = re-embed everything (vectors from different models live in different spaces).
384 dims (small, fast) vs 768/1024 (richer, more RAM). Start small, measure, upgrade only if recall says so.

6 · RAGCOMING · phase 3

Qdrant: a database for vectors

  • Point = id + vector + payload (JSON metadata). Collection = a set of points with the same vector size and distance metric.
  • Multitenancy: one collection for all customers + an indexed workspace_id payload field marked as tenant key. Forget the filter = one customer sees another's schema.
  • Qdrant stores sparse vectors (BM25-style keyword weights) next to dense ones → hybrid search with server-side RRF fusion.

HNSW: how search stays fast

HNSW (Hierarchical Navigable Small World): a layered graph. Start at the sparse top layer, greedily hop toward the query, drop a layer, repeat. It's ANN (approximate nearest neighbour): it may miss the exact best match rarely, but it's orders of magnitude faster than comparing against every vector.
Why Qdrant instead of FAISS?
FAISS is a library: an in-process index; you build persistence, filtering, multi-tenancy and an API yourself. Qdrant is a database server: REST/gRPC API, payload filters, snapshots, sparse+dense hybrid, horizontal scaling.

6 · RAGCOMING · phase 4

Two kinds of search

BM25 · lexical (keywords)

  • scores documents by matching words
  • rare words count more (IDF: “cust_ltv” > “id”)
  • repeating a word helps less and less (saturation, k1)
  • long documents are normalised (b)

✓ exact identifiers: cust_id, tbl_ord_hdr

✗ blind to synonyms: “buyers” ≠ “customers”

Dense · semantic (embeddings)

  • compares meaning via vectors
  • “buyers” ≈ “customers”, “income” ≈ “revenue”
  • works across phrasing and typos
  • needs an embedding model + vector index

✓ paraphrases and vague questions

✗ weak on rare codes and exact names

Hybrid search + Reciprocal Rank Fusion

Run both searches, then merge the rankings (not the raw scores, which live on different scales):

RRF(d) = Σlists 1 / (k + rank(d)) with k = 60
tableBM25 rankdense rankRRF scorefinal
orders121/61 + 1/62 = 0.0325🥇 1
customers311/63 + 1/61 = 0.03232
payments2—1/62 = 0.01613
buyers_v2—31/63 = 0.01594
  • Documents that both searches like float to the top: agreement wins.
  • k = 60 damps the difference between rank 1 and rank 2, so one list can't dominate.
  • No score normalisation needed: only positions are used. That's why RRF is the default fusion in most vector DBs, Qdrant included.
Why not just add the two scores?
BM25 scores are unbounded (e.g. 7.3, 12.9) while cosine similarity is in [−1, 1]. Adding them lets one scale dominate. RRF uses ranks only, so it needs no tuning to combine heterogeneous retrievers.

7 · RAG evaluationCOMING · phase 5

Retrieval metrics, worked by hand

The question needs 3 tables: orders, customers, order_items. Our retriever returns this top-5:

MetricFormulaHereAsks…
Precision@5relevant retrieved ÷ k2 / 5 = 0.40how much junk did we fetch?
Recall@5relevant retrieved ÷ all relevant2 / 3 = 0.67did we miss anything?
Hit rate@51 if any relevant in top-k1did we get at least one?
MRR1 ÷ rank of first relevant (averaged over questions)1 / 1 = 1.0how soon is the first good hit?
nDCG@5DCG ÷ ideal DCG0.70 (below)are relevant items ranked high?
nDCG step by step (relevance 1 = relevant, 0 = not; position i is discounted by log₂(i+1)):
DCG = 1/log₂2 + 0/log₂3 + 1/log₂4 + 0 + 0 = 1 + 0 + 0.5 = 1.500 IDCG = 1/log₂2 + 1/log₂3 + 1/log₂4 = 1 + 0.631 + 0.5 = 2.131 (perfect order: 3 relevant first) nDCG = 1.500 / 2.131 = 0.70
For text-to-SQL, recall is king: one missing table = a broken JOIN. We'd rather send 6 tables with 1 extra than 4 with 1 missing. Rerankers then fix precision.
MRR vs nDCG?
MRR only looks at the first relevant hit (good when one answer suffices). nDCG rewards the whole ranking, with graded relevance; better when several items are needed, like our tables.

Text-to-SQL: exact match vs execution accuracy

  • Valid-SQL rate: does it parse for the dialect (sqlglot)? Cheapest check, run on everything.
  • Exact match (EM): same text/AST as gold. Too strict: many correct queries look different.
  • Execution accuracy (EX): run predicted and gold SQL on a seeded sandbox database and compare result sets. The gold standard (used by Spider & BIRD).
LLM-as-judge: a strong model grades answers against a rubric. Known biases: position (prefers the first option), verbosity (prefers longer), self-preference (likes its own family's outputs). Mitigate: clear rubrics, swap order, spot-check with humans.

8Agents

An agent is an LLM that decides what to do next: it calls tools, looks at the results and loops until the task is done. Agent = LLM (brain) + tools (hands) + state/memory + a control loop.

Use the least autonomy that solves the problem. Our SQL flow is mostly a fixed graph with a few LLM decisions, not a free-roaming agent.

Tool calling, step by step

Can the LLM run code or query the database by itself?
No. It outputs a structured request (tool name + JSON arguments). Our application validates it, executes it with our permissions, and returns the result as a message. That boundary is where guardrails live.

LangGraph: agents as state machines

  • State: a typed dict shared by all nodes.
  • Node: a function state → partial update (may call an LLM or a tool).

9 · Memory managementCOMING · phase 6

9Memory management

LLMs are stateless: every call starts from zero. “Memory” is whatever we decide to put back into the context window.

The context budget (it all has to fit)

  • trim: keep only the last N turns
  • summarise: fast model compresses old turns into a paragraph
  • retrieve: store past turns as vectors, fetch only relevant ones (memory as RAG)
  • drop tool outputs once used (big schema cards add up fast)

Memory types (LangGraph vocabulary): semantic = facts (“user prefers MySQL”), episodic = past experiences/examples (a query the user corrected), procedural = instructions (prompt rules the agent refines).

Memory is user data: tenant-isolated, and deleted with the account.

10 · Human-in-the-loopCOMING · phase 6

10Human-in-the-loop

HITL = the graph pauses at a chosen point, a human answers / approves / edits, and the graph resumes exactly where it stopped.

Patterns

  • approve / reject a risky action
  • edit state: fix tables or SQL before continuing
  • answer a clarification: “gross or net revenue?”
  • review tool calls before they run

Where SQLAssist uses it

  • ambiguous question → ask instead of guessing
  • confirm selected tables before generating
  • any non-SELECT statement needs explicit approval
from langgraph.types import interrupt, Command def approval(state): decision = interrupt({"sql": state["sql"]}) return {"approved": decision["approved"]} # later, when the user clicks Approve: graph.invoke(Command(resume={"approved": True}), config={"configurable": {"thread_id": "42"}})
HITL requires a checkpointer (Postgres-backed in production) so a paused run survives restarts, and the same thread_id to resume the right run.
Why HITL instead of a better prompt?
Some decisions need information or authority only the human has (which revenue definition, whether deleting is OK). Prompts can't create that; a pause can. It also builds trust and audit trails.

12 · Guardrails, shipping & scaleCOMING · phases 8–9

12Guardrails & scale

Defense in depth

  • Prompt injection: text that tries to override instructions. It can arrive in the question or in retrieved content (a malicious schema comment!) → treat retrieved text as data. Groq hosts Llama Prompt Guard 2 classifiers for this.
  • Read-only policy: parse generated SQL with sqlglot and block DROP / DELETE / UPDATE / ALTER unless a human approves (chapter 10).

Rate limiting (token bucket): each user's bucket holds N tokens and refills at r/second; each request takes one; empty → 429 Too Many Requests. Protects us and our Groq free-tier quota. Plans get different buckets.

Caching: exact cache (same prompt hash → stored answer) and semantic cache (a new question whose embedding is ~0.95 similar to a past one reuses the answer). Key it by workspace + schema version or users see stale or foreign answers.

Constrained decoding: the decoder may only sample tokens that keep the output valid for a schema.

Context window: max tokens a model can attend to in one call (input + output).

CORS: browser rule; servers must allow other origins to read their responses.

Cosine similarity: angle-based similarity of two vectors, −1 … 1.

Cross-encoder: reads query + document together to score relevance; used for reranking.

Dependency injection: a function declares needs; the framework provides them.

Embedding: vector of numbers representing meaning; similar meaning → close vectors.

Event loop: single thread that runs async tasks, switching at await points.

Execution accuracy (EX): predicted SQL returns the same rows as the gold SQL.

Faithfulness: answer is fully supported by the retrieved context.

Fallback: switch to an alternative (e.g. another model) when the first choice fails.

FastMCP: Python framework for building MCP servers with decorators.

Fine-tuning: further training a model's weights on your examples.

Golden dataset: hand-checked questions with known correct answers for evaluation.

Groq: inference provider running open LLMs on custom LPU hardware.

Guardrail: check that blocks or fixes unsafe inputs/outputs around an LLM.

HITL: human-in-the-loop; the graph pauses for a human decision, then resumes.

Idempotent: repeating a request has the same effect as doing it once (PUT, DELETE).

JSON-RPC: lightweight request/response protocol; the wire format of MCP.

JSONB: PostgreSQL's binary JSON type: queryable and indexable.

JWT: signed token (header.payload.signature) carrying claims like user id + expiry.
